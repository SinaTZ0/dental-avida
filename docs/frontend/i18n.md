# Languages (i18n)

The app serves Persian (`fa`, right-to-left) at unprefixed paths. Every piece of text a person reads is a message
from [Paraglide JS](https://paraglidejs.com), a compiler
that turns each message into a typed function. A message is a plain function call, with no provider and no hook, so it
works the same in components, loaders, `head`, schema checks and server code.

These are the rules. The page and feature steps link here from [frontend-flow.md](../frontend-flow.md) and
[backend-flow.md](../backend-flow.md).

## The Pieces

| Piece                | Where                                            | Job                                                                         |
| -------------------- | ------------------------------------------------ | --------------------------------------------------------------------------- |
| Project settings     | `project.inlang/settings.json`                   | The base locale, the locales, where the message files are.                  |
| Compiler config      | `project.inlang/paraglide.config.ts`             | How a request's locale is found, the URL patterns, excluded routes.         |
| Messages             | `messages/fa.json`                               | Persian user-facing text.                                                   |
| Generated code       | `src/paraglide/` (gitignored)                    | `m.<key>()` functions and the runtime. Never edit; it's regenerated.        |
| Server middleware    | `paraglideMiddleware` in `src/server.ts`         | Finds each request's locale and keeps it for everything that request runs.  |
| URL rewrite          | `rewrite` in `src/router.tsx`                    | Keeps routes and links aligned with the configured URL patterns.            |
| Locale for API calls | `src/orpc/client.ts`, `src/lib/locale.server.ts` | The browser sends its locale in `x-locale`; the server reads it on `/rpc`.  |
| Formatting helpers   | `src/lib/locale.ts`                              | `formatNumber`, `formatDate` and friends, Open Graph codes, language names. |
| Switcher             | `src/components/shared/locale-switcher/`         | Hidden while Persian is the only locale.                                    |

The Vite plugin compiles the messages in `pnpm dev`, `pnpm build`, Storybook and Vitest. `pnpm i18n:compile` does it
on its own, and runs before `tsc` in `pnpm typecheck` and after `pnpm install`.

**The inlang plugins.** `settings.json` names two plugins by their jsDelivr URL, each pinned to a version: the message
format and the `m.key()` matcher. Every compile downloads them and keeps a copy in `project.inlang/cache/plugins/`,
which it falls back to when the download fails. With neither, the compiler writes no messages and still reports
success. So the copies are committed (`git add -f`, since inlang ignores its own folder), and a build works on a
server or a CI runner that can't reach jsDelivr. After changing a plugin's version, run `pnpm i18n:compile` online
and commit the new file; `pnpm lint` fails until it's there (`scripts/i18n-check.mjs`).

`pnpm dev`, Vitest and `pnpm i18n:compile` all write the same file layout: one module per locale (`outputStructure`
in `paraglide.config.ts`, `--output-structure locale-modules` on the CLI). They share `src/paraglide/`, so a different
layout from each would rewrite the folder under a running dev server every time `pnpm typecheck` ran. That rules out
Paraglide 3's default for Vite, `virtual-modules`: the CLI can't write it. `pnpm build` writes one module per message
(set in `vite.config.ts`), so unused messages drop out of the bundle.

## How the Locale Is Found

- **Pages** use plain Persian paths such as `/notes`. The Paraglide URL strategy falls back to `fa`. Cookies and
  `Accept-Language` play no role in locale selection.
- **On the server**, `paraglideMiddleware` resolves the locale once per request and keeps it in `AsyncLocalStorage`.
  `getLocale()` returns it anywhere in that request, including oRPC procedures that loaders call in-process during
  SSR.
- **In the browser**, `getLocale()` reads `window.location`.
- **`/rpc/*` has no locale in its path**, so the browser's `RPCLink` sends `x-locale: <locale>` and the
  `custom-locale-header` strategy reads it. A missing or unknown value falls back to the base locale.
- **Excluded routes** (`/api/*`, `/healthz`, `/robots.txt`, `/sitemap.xml`) are never redirected or prefixed. Better-Auth
  returns error codes, which the auth forms turn into messages (`describeAuthError` in `src/lib/auth-errors.ts`).
- **Route declarations and links** in `src/routes.ts` and `<Link to>` use plain paths such as `/notes`. The router
  applies the configured Paraglide URL patterns to navigation. Use `localizedPath` (`src/lib/locale.ts`) with
  `redirect({ href })` when a path bypasses the router rewrite.

## Writing Messages

- **Every piece of text a person reads is a message**: labels, headings, button text, placeholders, `aria-label`s,
  `sr-only` text, alt text, toasts, page titles and descriptions, form and API error messages. Code identifiers, logs
  and developer diagnostics stay in English and are not messages.
- **Add each key to `messages/fa.json`.** `pnpm lint` checks for empty messages (`scripts/i18n-check.mjs`).
- **Key names are flat snake_case, prefixed by their owner:**

  | Prefix             | For                                            | Example                          |
  | ------------------ | ---------------------------------------------- | -------------------------------- |
  | `common_`          | Words several places share, primitives' labels | `common_close`, `common_loading` |
  | `site_`, `nav_`    | Site identity, the header and footer           | `site_name`, `nav_notes`         |
  | `<slice>_`         | One route slice                                | `notes_empty`                    |
  | `<feature>_error_` | Messages the API sends (validation, outcomes)  | `note_error_title_required`      |

  Name a key after what it is, not where it sits on the screen (`notes_delete_confirm`, not `notes_button_2`). Delete a
  key when its last use goes.

- **Values are parameters**, never string concatenation: `"notes_delete_label": "حذف «{title}»"`, called as
  `m.notes_delete_label({ title })`. Word order differs between languages, so a sentence is always one message.
- **Numbers are formatted by the message.** Pass the number and declare it as `number` in the message to get Persian
  digits and separators (`۱٬۲۰۰`).

  ```json
  "note_error_title_too_long": [
    {
      "declarations": ["input max", "local maxText = max: number"],
      "match": { "": "عنوان حداکثر {maxText} حرف است." }
    }
  ]
  ```

- **Counting** in Persian uses the same noun form after any number, so one message variant is enough.

### Never Call a Message at Module Scope

A module is evaluated once per server process. A message called at its top level is frozen in the locale of whatever
ran first, and every later request, in any language, gets that text. Call messages when the text is needed: in render,
in a handler, in a function.

```ts
// Wrong: evaluated once, in one locale, for every request
const NAV_ITEMS = [{ label: m.nav_home(), to: "/" }];

// Right: store the message function, call it in render
const NAV_ITEMS = [{ label: m.nav_home, to: "/" }] as const; // {item.label()}

// Right: a check's `text` is called each time an issue is formatted
const Title = Schema.String.check(Schema.isMinLength(1, { text: () => m.note_error_title_required() }));
```

Schemas are module-level constants, so a check never holds finished text. Its message goes in the `text` annotation
(`src/lib/schema.ts`), which takes a function only: `standardSchema` and `issueToErrorData` call it when they format
an issue, in the locale of the page or the request that formats it.

The same holds for anything that becomes text later: export a function (`rateLimitedMessage()`), not a string
constant.

## Messages from the API

The API sends finished text in its error data (`errors`, `fields`), and `describeApiFailure` shows it as it is
([backend/architecture.md](../backend/architecture.md) → Errors are uniform and safe). That text is in the request's
locale:

- Validation schemas (`validation.ts`) and form schemas (`schema.ts`) give every check a `text` function. A service
  that refuses its input fails with `InvalidInput`, which holds the schema issue, not text. `effectProcedure` formats
  it with `issueToErrorData` after the Effect has run, in the request's own context, so the messages come out in the
  request's locale.
- A feature's own failures are tagged errors that carry facts. The procedure's `errors` map writes their text when it
  turns one into a contract error (`imageUnusable()` in `src/orpc/note/procedure.ts`:
  `fields: { imageMediaId: m.note_error_image_unusable() }`). Services, repositories and jobs never import messages.
- The `message` of a contract error (`commonErrors`, `authErrors`) is a developer diagnostic in English. It never reaches
  a form.

## Editable Content

Messages are compiled into the build. Editable fields that use `LocalizedText` store a required `fa` value in `jsonb`,
for example `{ fa: "اخبار" }` (`src/lib/localized-text.ts`). The service reads it with `localize(text)`
(`localizeOptional` for a nullable column) and sends the client plain strings.

## Numbers, Dates and Direction

- **Numbers and dates outside messages** go through `formatNumber(value)` and `formatDate(value, options)`
  (`src/lib/locale.ts`). They use the current locale, so Persian gets Persian digits and the Jalali calendar. Never
  build an `Intl` formatter with a fixed locale. Dates are shown in one time zone for everyone, `APP_TIME_ZONE`
  (`Asia/Tehran`; change it for a project whose readers live elsewhere): a formatter without one uses its machine's
  zone, so the server and the browser would print different days for the same moment and React would replace the
  text on hydration. The same file has `formatDateRange` for spans, `formatDateParts` for separate day, month and year
  values, and `formatRelativeDays` for strings such as «فردا». A calendar date stored without a time (`2026-10-30`)
  becomes a `Date` through `isoToDate`,
  at UTC noon, so it's the same day in every time zone.
- **Input** is normalized whatever the page's language: `toLatinDigits` before parsing a number, the `PersianText`
  schema (`src/lib/schema.ts`) for free text ([backend/architecture.md](../backend/architecture.md)).
- **Direction** comes from the locale: `<html lang dir>` and Base UI's `DirectionProvider` read `getTextDirection()` in
  `__root.tsx`. Components never assume a direction:
  - Use logical classes such as `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`, and `rounded-s-`.
  - In Persian, forward arrows point left and back arrows point right. Follow the text direction when setting icons.
  - Set `dir="ltr"` for left-to-right text such as emails, URLs, phone numbers and codes.
- **Content** (a note's title, a user's name) is stored as typed and isn't translated.

## Links

- Use `Link` with the plain path. The header's language switcher renders only when another locale is configured.

## SEO

`pageMeta` (`src/lib/seo.ts`, [seo.md](./seo.md)) builds the locale tags itself:

- The canonical URL and `og:url` use the unprefixed page path.
- `og:locale` is `fa_IR`. Language alternates apply when there is more than one locale.
- The sitemap lists each public Persian page once.

`title` and `description` passed to `pageMeta` are messages, called in `head`.

## Adding a Language

**Adding** (say Arabic, `ar`):

1. Add it to `locales` in `project.inlang/settings.json`, and to both `urlPatterns` entries in `paraglide.config.ts`
   (`["ar", "/ar"]`, `["ar", "/ar/:path(.*)?"]`), above the base locale's line.
2. Copy `messages/fa.json` to `messages/ar.json` and translate every value.
3. Add its Open Graph code to `OG_LOCALE` and its own name for itself (`العربية`) to `LOCALE_NAMES`, both in
   `src/lib/locale.ts`.
4. Check it in both directions: an RTL language needs nothing more if the components use logical classes.

## Checklist for a New Page

1. Page copy, metadata, and form and API messages come from `messages/fa.json`. Call them at render or request time.
2. Numbers and dates go through the message's `number` declaration, `formatNumber` or `formatDate`.
3. Check the right-to-left layout and directional icons at desktop and phone widths.
4. Links use `Link` with the plain path.
